# 로그인 흐름 리팩토링 TODO

## 합의한 동작

- 모달과 CTA는 같은 로그인 진입 함수와 `returnTo` 전달 방식을 사용한다.
- 로그인 진입은 `replace`, 성공 후 복귀도 `replace`를 사용한다.
- 로그인 화면의 상단 뒤로가기도 같은 `returnTo`로 `replace`한다. 브라우저 자체 뒤로가기는 실제 기록을 따른다.
- 앱에서 `A → B → 로그인 → B 복귀` 후 뒤로가기는 A로 이동한다. 로그인 전 B 기록을 추가로 남기지 않는다.
- 웹의 외부 인증 기록은 남아도 된다. 인증된 사용자가 과거 `/login` 기록에 도착하면 `returnTo` 규칙으로 목적지를 결정해 `replace`한다. 해당 로그인 기록은 목적지 기록으로 교체되고, 다음 뒤로가기는 그 기록보다 앞쪽으로 이동한다.
- 복귀 목적지는 `returnTo` 쿼리 → sessionStorage → 홈 순서로 결정한다. 쿼리가 존재하지만 비어 있거나 유효하지 않으면 저장소를 사용하지 않고 홈으로 이동한다.
- 인증된 사용자의 `/login` 직접 진입도 같은 목적지 우선순위를 사용한다.

## 진행 방식

- 각 단계에서 구현 → 관련 자동 검증 → 가능한 실제 흐름 확인 → 변경 코드 설명 및 사용자 검토를 진행한다.
- 다음 단계의 구현은 앞 단계의 코드 검토를 마친 뒤 진행한다.
- 실제 인증을 우회하거나 목킹하지 않는다. 앱 WebView 검증과 일반 브라우저 검증 결과를 구분한다.
- 제품 코드 변경과 검증 결과는 각 단계 완료 시 기록한다.

## 결정한 취소 동작과 후속 작업

- 성공과 상단 뒤로가기는 동일한 `returnTo`를 사용한다. 문의 작성 목적지라면 취소도 문의 작성으로 이동한다.
- MBTI도 성공과 상단 뒤로가기는 같은 `returnTo`를 사용한다. 공통 로그인은 MBTI 목적지를 판별하거나 MBTI 전용 실패 이동을 처리하지 않는다.
- MBTI 본인 결과 화면에서 세션 확인 후 비로그인 상태면 결과·진행 상태를 초기화하고 첫 화면으로 `replace`한다. 결과 조회도 인증 확인 후 시작한다. 공유 결과(`shared=1`)의 기존 공개 열람은 유지한다.
- [ ] 문의 작성 페이지의 인증 가드 도입 및 비로그인 복귀 동작 검토. 현재 페이지 진입 가드는 없고 작성 버튼과 등록 API에서 인증을 확인한다. 이번 단계에서는 인증 가드를 추가하지 않았다.

- 미확인: 실제 소셜 인증 실패, Flutter 실행. 세션 로딩·소실에 따른 화면 변화는 자동 테스트로 검증했다.

## 3단계 검증

- 진입 처리 통합 후 관련 기존 테스트 19건 통과(인증 흐름에서 10건 선택, 진입·취소 9건). 변경 제품 파일 ESLint와 `git diff --check` 통과. Playwright에서 기존 인증 세션의 직접 진입 → returnTo 이동, 비로그인 세션의 로그인 화면 유지·목적지 저장을 확인했다. 새 소셜 인증·실제 bfcache·Flutter는 이번 변경 후 재실행하지 않았다.
- 관련 Jest 7개 스위트, 100개 테스트 통과. 새 회귀 확인 4건 중 3건은 변경 전 실패했고, 변경 후 모두 통과했다.
- 기존 인덱스·로그인 마커가 남아 있는 기록도 인증된 진입이면 query 목적지로 한 번만 replace한다.
- bfcache에서 복원된 비인증 메모리는 세션 복원 후 이동한다. 이미 인증된 메모리에서는 세션 복원이 상태 변경을 발생시키지 않아도 이동한다. 세션 복원 요청은 기존 공유 Promise로 중복 방지한다.
- 타입 검사: `pnpm exec tsc --noEmit --incremental false` 통과. 변경한 제품 파일 ESLint 오류·경고 없음. `git diff --check` 통과.
- Playwright MCP / 기존 실제 인증 세션 / 인증 우회·목킹 없음:
  - A → 로그인 문서 → 외부 문서(`localhost:8123`) → B 기록을 실제 문서 이동으로 구성했다. 로그인 문서 commit 직후 외부 문서로 이동해 과거 로그인 기록을 남겼으며, 실제 OAuth 인증을 수행한 것은 아니다.
  - B에서 뒤로가기 → 외부 문서 유지 → 뒤로가기 → 과거 로그인 문서 도착 → returnTo의 B로 replace 확인.
  - history.length는 복귀 전후 5로 유지. 최종 B 화면에 로그인 버튼이 없고 returnTo 저장소는 정리되어 있음 확인.
  - 그다음 뒤로가기는 A, 앞으로가기는 교체된 B로 이동 확인.
- 미확인: 새 소셜 인증 후 실제 외부 인증 페이지 기록과 bfcache 복원, Flutter 실행. bfcache 이벤트·인증 상태에 따른 분기는 자동 테스트로 확인했다.

## 최종 정리: 복원 이벤트 책임과 테스트 간소화

- `pageshow` 리스너는 AuthProvider 한 곳에만 둔다. Provider는 서버 세션 재확인 후 구독한 화면에 결과를 전달하고, 로그인 경로 판단·returnTo 조회·이동은 로그인 페이지에서 처리한다.
- 로그인 화면은 최초 진입 시 세션을 확인하고 복원 결과를 구독한다. 컴포넌트 정리 시 구독을 해제하고 진행 중인 최초 확인의 이동을 취소한다. 로그인 성공에 따른 인증 상태 변경은 이동 effect를 실행하지 않아 약관 분기와 충돌하지 않는다.
- `restoreAuthSession({ force: true })`는 복원된 메모리의 인증 상태를 재사용하지 않고 기존 `/api/auth/session`을 호출한다. 진행 중인 복원 요청은 기존 Promise로 공유한다. 캐시가 인증 상태여도 서버가 비로그인으로 응답하면 로그인 화면에 남는다.
- 모달·CTA 통합 테스트와 중복된 LoginModal 단독 테스트를 제거했다. 소셜 로그인 중복 성공 사례를 정리하고 URL 보안 검증은 같은 규칙의 입력을 묶었다. 기존 URL 보안 입력 사례는 유지하고 저장 횟수 같은 구현 세부사항 검증을 제거했다.
- 최종 자동 검증: 관련 Jest 6개 스위트, 83개 테스트 통과(이전 7개 스위트 100개). 타입 검사 통과. 변경 제품 파일 ESLint 오류 없음, 기존 MBTI img 경고 1개 유지. `git diff --check` 통과.
- 최종 브라우저 재검증은 Playwright MCP 연결이 종료되어 진행하지 못했다(`Transport closed`, 코드 실행과 탭 목록 모두 실패). 이전 단계의 실제 브라우저 결과와 이번 자동 테스트 결과를 구분한다. 이번 복원 이벤트 연결·서버 재확인은 실제 bfcache·Flutter 검증 완료로 간주하지 않는다.
