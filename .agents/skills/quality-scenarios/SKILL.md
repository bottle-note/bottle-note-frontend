# 품질 시나리오 도출

기능을 구현하기 전에 무엇을 어느 수준까지 만들지 정한다. 구현 방법은 여기서 정하지 않는다.

읽을 것: `references/quality-model.md`(품질 특성, 합격 기준), `references/baseline.md`(공통 기준선)

## 입력

- 기능 목표: 사람이 정한 그로쓰 목표 (예: 비회원 로그인 전환율 개선)
- 확정된 유저 시나리오: 사용자가 어떤 순서로 무엇을 하고 무엇을 보는지

유저 시나리오가 확정되지 않았으면 요청에서 초안을 써서 사람에게 확인받고 시작한다.

## 절차

1. 유저 시나리오를 단계로 나눈다.
2. 단계마다 기능 시나리오(F)를 쓴다. 이미 구현된 동작도 시나리오에 있으면 F로 쓰고, 현재 코드와 다른 점은 「조율할 것」에 적는다.
   - 기능 목표를 잴 GA4 이벤트가 필요하면 F로 쓰고 `.agents/skills/bottle-note-ga4/SKILL.md`를 따른다.
3. 단계마다 걸리는 품질 특성 › 하위 특성을 `quality-model.md` 1절에서 고르고 품질 시나리오(Q)를 쓴다.
   - 기준선 항목을 그대로 적용하면 되는 내용은 Q로 쓰지 않고 기준선 번호만 고른다.
   - 기준선 항목을 이 기능에 맞게 구체화해야 하면 Q로 쓰고 이름 옆에 기준선 번호를 적는다. 예: `Q4 추천 실패 격리 (B2)`
   - 맞는 특성이 없으면 가장 가까운 특성을 고르고 「조율할 것」에 적는다.
4. Q의 합격 기준을 정한다. 표준이 있으면 `quality-model.md` 2절 값을, 없으면 3절 규칙을 따른다. 기존 코드의 현재 수준을 기준으로 삼지 않는다.
5. 기능에 해당하는 기준선 번호를 `baseline.md`에서 고른다.
6. 빠짐과 과잉을 점검한다.
   - 빠짐: F도 Q도 기준선도 걸리지 않은 유저 시나리오 단계
   - 과잉: 유저 시나리오 어느 단계에도 연결되지 않는 Q
7. 영향 범위와 PR 분할을 정한다.
   - 영향 범위는 유저 시나리오에서 사용자가 무언가를 보거나 하는 페이지까지다. 다른 기능으로 넘어가기만 하는 페이지는 진입점까지만 넣는다. 표준 미달 개선도 영향 범위 안에서만 한다.
   - PR마다 통과시킬 F·Q 번호와 건드리는 페이지를 적는다. 그 시나리오들이 PR 하나 안에서 검증까지 끝나는 단위로 나눈다.
   - 성능 기준 미달의 원인이 이번 변경이면 기능 PR 안에서 고친다. 원인이 기존 코드면 개선 PR을 따로 만들고, 기능 PR에는 그 Q를 개선 PR 번호와 함께 적는다.
8. 아래 형식으로 출력하고 멈춘다. 사람이 합격 기준과 분할을 조율해 확정하면 구현을 시작한다.

## 출력 형식

PR 본문 「품질 목표」 섹션에 그대로 쓴다. 번호는 기능 단위로 1부터 매기고, PR 분할은 이 번호를 나눠 가진다.

```markdown
## 품질 목표

기능 목표: <사람이 정한 목표>

### 기능 시나리오

- F1 Given <누가, 어떤 상태> / When <행동> / Then <결과> — <확인 방법>

### 품질 시나리오

- Q1 <이름> · <특성> › <하위 특성>
  - Given <누가, 어떤 환경>
  - When <행동이나 사건>
  - Then <화면이 어떻게 되어야 하는지>
  - 합격 기준: <수치나 예/아니오> (근거: <표준 이름 또는 유저 시나리오에서 찾은 이유 한 문장>)
  - 확인 방법: <자동 / 에이전트 리뷰 / 수동>

### 적용 기준선

B1, B2, ...

### PR 분할

- PR 1: F1, Q1 — <건드리는 페이지>

### 조율할 것

- <사람이 정해야 하는 쟁점, 현재 코드와 시나리오의 차이, 근거를 정하지 못한 합격 기준>
```

확인 방법은 판정을 누가 하느냐로 고른다. 가능한 한 자동 쪽을 고른다.

- 자동: 명령을 실행하면 통과/실패가 나온다. 테스트, lint, 타입 검사, Lighthouse
- 에이전트 리뷰: 도구는 없지만 코드를 읽으면 예/아니오로 답할 수 있다
- 수동: 실제 환경에서 직접 조작하거나 봐야 안다. 앱 WebView, 실기기, 실제 로그인 세션

한 항목에 확인 방법이 둘이면 경로를 나눠 적는다. 예: 브라우저는 자동(RTL), WebView는 수동

## 확정 후 구현 규칙

- 확정된 F·Q의 합격 기준과 그걸 검증하는 테스트는 구현 중에 바꾸거나 완화하지 않는다. 바꿔야 하면 사람과 다시 조율한다.
- 테스트는 Given·When·Then 구조를 따른다. Given은 렌더링 조건과 API 응답 대역, When은 사용자 입력, Then과 합격 기준은 화면 확인이다.
- 테스트 이름에는 번호 대신 시나리오 문장을 쓴다. 번호는 기능마다 새로 매겨지므로 번호와 테스트의 연결은 PR 본문 검증 결과에 남긴다.
- 자동 테스트는 React Testing Library 컴포넌트 통합 테스트를 중심으로, 관련 컴포넌트를 함께 렌더링해 사용자 입력부터 화면 결과까지 확인한다. 실행 도구는 저장소의 테스트 설정을 따른다.
- 내부 함수 호출, 컴포넌트 분리 방식, 상태 변수 같은 구현 세부사항에 테스트를 결합하지 않는다. API 응답 대역은 OpenAPI 계약을 따르며, 실제 서버 연동 검증으로 간주하지 않는다.
- 설계 결정은 PR 본문 「설계 결정」에 `D1 <결정 한 줄> ← Q1 — ADR 작성/없음`으로 적는다. 근거 Q가 없는 구조 변경은 하지 않는다.
- 코드로 복원되지 않는 설계 결정은 `adr/README.md` 규칙으로 ADR을 남긴다.
- 구현이 끝나면 `quality-gate` 스킬로 검증한다.
