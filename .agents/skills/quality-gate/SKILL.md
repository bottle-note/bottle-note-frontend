# 품질 게이트 검토

PR 본문 「품질 목표」의 F·Q·B가 합격 기준을 통과했는지 판정한다. 코드를 고치지 않고 판정만 한다.

읽을 것: PR 본문(또는 확정된 「품질 목표」), 변경 diff, `../quality-scenarios/references/quality-model.md`, `../quality-scenarios/references/baseline.md`

## 원칙

- 구현한 에이전트와 분리해서 실행한다. 별도 세션이나 서브에이전트에서 실행한다.
- 확정된 합격 기준으로만 판정한다. 기준이 모호하면 통과로 해석하지 않고 「사람 확인 필요」로 적는다.
- 실행하지 않은 검사는 통과로 적지 않는다. 실행할 수 없으면 「측정 못 함」과 이유를 적는다.

## 절차

1. 「품질 목표」에서 F·Q·B 번호와 합격 기준, 확인 방법을 읽는다.
2. 자동 검사를 실행한다.
   - 테스트: `pnpm test`. 각 F·Q에 대응하는 테스트를 이름으로 찾아 연결한다. 대응 테스트가 없으면 실패로 적는다.
   - lint: `pnpm lint`
   - 타입 검사: `pnpm exec tsc --noEmit`
   - 성능·접근성: 로컬 프로덕션 빌드나 프리뷰 URL에 Lighthouse 모바일 검사를 실행하고 `quality-model.md` 2절 기준과 비교한다.
     - 시나리오의 Given과 같은 로그인 상태로 잰다. 로그인이 필요하면 사용자에게 로그인 세션을 요청한다.
     - 데이터가 많은 대표 페이지(예: 리뷰와 이미지가 많은 주류 상세)를 고르고, 측정한 URL을 결과에 적는다.
     - 3회 재서 중앙값으로 판정한다.
3. 에이전트 리뷰 항목은 diff와 관련 코드를 읽고 예/아니오로 판정한다. 판정 근거가 된 파일과 줄을 적는다.
4. 브라우저에서 확인할 수 있는 항목은 현재 환경에서 연결 가능한 브라우저 도구로 시나리오의 입력·클릭·이동을 직접 수행하고 결과를 적는다.
   - 변경과 관련된 스크롤, 고정 영역, 키보드, 반응형 동작도 확인한다. 사용자가 제시한 viewport가 있으면 같은 조건으로 확인한다.
   - 무한 스크롤은 로딩 감지 요소 진입 전후의 네트워크 요청과 화면 결과를 비교한다.
   - 로그인이 필요하면 사용자에게 로그인을 요청하고 인증된 세션을 쓴다. 실제 인증 흐름은 우회하거나 목킹하지 않는다.
   - 앱 WebView 전용 동작처럼 브라우저로 확인할 수 없는 항목은 「수동 확인 필요」로 모은다.
   - 반복 실행할 Playwright E2E 테스트 코드는 만들지 않는다.
5. 범위를 점검한다.
   - 「PR 분할」에 없는 페이지가 diff에 들어 있는지
   - 근거 Q 번호가 없는 설계 결정이 있는지
   - 확정된 합격 기준이나 그걸 검증하는 테스트가 구현 중에 바뀌거나 완화됐는지
6. PR 본문에 「검증 결과」를 작성한다.

## 출력 형식

```markdown
## 검증 결과

- F1 통과 — <테스트 파일 › 테스트 이름>
- Q1 실패 — LCP 3.1초 (기준 2.5초, Lighthouse 모바일)
- Q2 통과 — 에이전트 리뷰: <근거 파일:줄>
- B5 측정 못 함 — <이유>
- 수동 확인 필요 — F2 WebView 로그인 왕복
- 범위 — <이상 없음 또는 발견한 문제>
```

실패, 측정 못 함, 수동 확인 필요 항목이 하나라도 있으면 PR을 머지할 수 있는 상태로 보고하지 않는다.
